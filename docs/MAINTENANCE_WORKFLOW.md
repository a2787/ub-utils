# OmniBlock 标准维护流程

这是本项目唯一的详细维护流程。每次 AI 接手、修改、验证或发布，都按本文件执行；如果流程本身需要变化，
必须同时更新 `AGENTS.md`、`docs/KNOWLEDGE_TREE.md` 和本文件，并在当前维护台账写明原因。

## 0. 接手与边界确认

先读 `AGENTS.md`、`docs/KNOWLEDGE_TREE.md`、本文件、`docs/maintenance/CURRENT.md`、`docs/maintenance/PLAN.md`
和 `docs/architecture/ARCHITECTURE.md`，再读与任务直接相关的
README 段落、源码和测试。执行 `git status --short`，把已有脏改动视为用户资产；不覆盖、不回退、不暂存无关改动。

先写出本轮范围：受影响的平台、用户可见行为、是否涉及存储/身份/网络/发布、需要的验证等级，以及明确不做的事项。
需求不清时先给出最合理的范围和风险；只有会改变任务边界、需要新权限或触碰红线时才暂停请求决定。
在 `PLAN.md` 选择或创建一个 `OB-*` 项，补齐范围、非目标、依赖、验收、证据和下一步；大改动必须先经过用户确认。

计划状态由 `proposed → approved → in_progress → verified` 组成，验证受阻时转为 `blocked`，暂缓时转为 `deferred`，
被新决定替代时转为 `superseded`。状态不能跳过证据直接写成 `verified`。

## 1. 复现与证据基线

修复前先用聚焦测试、人工合成夹具或只读真实探针复现。不能复现时记录原因，不得直接把推测当根因。
每个缺陷至少新增或更新一个回归断言；条件允许时，断言应在旧行为上失败，证明它确实锁住了本次缺陷。

三类证据必须分开写：

- **`real-site verified`**：生产网站浏览器中实际观察到的结果，必须写日期、脱敏页面形式、登录状态和确切结果。
- **`structure regression`**：本地夹具或已捕获 DOM 契约通过，只证明代码路径，不证明线上结构仍未变化。
- **`blocked`**：登录、验证码、限流、导航竞态或数据不可用导致无法验证，必须写明原因，不能改写成通过。

探针只读：可以导航、滚动、展开、悬停、暂停播放和点击脚本自身 UI；不得点击平台举报、官方拉黑、关注、发帖等
写入控件，不读取或导出 Cookie。登录态探针只在用户对本轮明确授权后执行，凭证由用户本人输入，探针使用内存测试存储。

## 2. 设计与实施顺序

按“最小范围、明确边界、可逆状态、失败关闭”的顺序实施：

1. 先确认身份键可靠性；无法可靠解析身份时，不提供可执行拉黑入口。
2. 先处理生命周期、观察范围和调度，再处理平台特例；避免用更高频轮询掩盖结构问题。
3. 对观察器、定时器、缓存、日志和 DOM 引用设上限；页面隐藏时暂停非必要工作，恢复时补同步。
4. 平台只对齐用户能力，不套用另一平台的选择器、层级或事件路径；新增选择器先由真实结构捕获确认。
5. 保持运行锁、GM 存储启动栅栏、用户脚本 document-start 顺序和跨页面状态边界。
6. 代码改动完成后主动运行受影响的测试和 `node --check omniblock.user.js`；不要注释错误或增加绕过标记。
7. 涉及架构边界、信任边界、数据格式或长期维护方式时，用一个短 ADR 记录一个决定；旧 ADR 不改写。

## 3. “注意更新”同步协议

“注意更新”是每轮的强制动作，不是发布前可选整理。修改结束、验证结束、发布结束各检查一次：

| 发生变化 | 必须更新 |
|---|---|
| 用户看到的入口、文案、范围、默认值或限制 | `README.md`、当前版本 changelog |
| 测试命令、通过/失败数字、真实站点、限制或下一步 | `docs/maintenance/CURRENT.md` |
| 维护规则、安全边界、发布门禁、文档路由 | `AGENTS.md`、`docs/KNOWLEDGE_TREE.md`、本文件 |
| 版本号、构建标识、源码快照、提交、tag、Release、raw 更新出口 | 当前 changelog、`CURRENT.md`、发布回写 |
| 计划状态、依赖、验收或架构决策 | `PLAN.md`、`ARCHITECTURE.md`、必要时 ADR |
| 文件移动、拆分、合并、归档 | 所有入口索引、相对链接、大小门禁 |

更新后用搜索检查旧状态残留，例如旧版本号、旧的“未发布/已发布”、过时命令和已经移动的路径；
不能只更新一份文档。历史事实只能追加或移动到归档，不得通过回写旧条目制造“从未发生过”的新叙述。

## 4. 文档大小与知识树治理

活动文档使用 UTF-8 字节预算：`AGENTS.md` 16 KiB、知识树 12 KiB、流程 24 KiB、当前状态 24 KiB、
根维护入口 16 KiB、根 changelog 24 KiB、单版本条目 24 KiB、README 64 KiB。`node test/docs-check.cjs`
负责自动检查这些边界和入口一致性。
活动计划 24 KiB、架构正文 24 KiB、单个 ADR 12 KiB；接近预算时先拆分，不把历史流水账挪进活动文件。

达到预算的处理顺序：

1. 删除重复说明，保留一个权威来源，其他位置只放链接和一句摘要。
2. 按“当前状态 / 流程规则 / 用户行为 / 版本条目 / 平台历史”拆分。
3. 为新文件命名、加标题和更新时间，立刻更新 `KNOWLEDGE_TREE.md`、根索引和相邻链接。
4. 原始历史内容移动到只读归档，不在归档中追加最新状态；需要纠正历史时新增小型更正条目。
5. 重组后运行 docs check、链接检查、隐私门禁和 `git diff --check`。

AI 每轮默认只读活动节点和任务相关节点；不要因为“可能有用”加载整份历史归档。任何新建文档都必须说明用途、
所有者、更新触发条件、大小预算和归档方式，避免再次形成无人维护的长篇流水账。

## 5. 验证矩阵

最低通用门禁：

```powershell
node --check omniblock.user.js
node test/docs-check.cjs
node test/run.cjs
git diff --check
```
受影响平台额外执行 `AGENTS.md` 中的聚焦测试和真实站点探针。改动 B站评论/弹幕跑 quickblock 与 B站探针；改动抖音、
微博等适配器跑 adapters 与对应探针；改动通用 UI、存储、Shadow DOM、日志或调度跑通用回归和性能边界回归。
真实探针即使被阻断也要运行并记录 `blocked`，不能用夹具通过替代。

## 6. 发布与关闭

只有当前任务上下文中的明确授权且发布边界满足时才公开发布；历史授权不自动继承。发布前：提升 userscript `@version`，同步 `RUNTIME_BUILD`、README、
当前版本 changelog 和 CURRENT；运行完整矩阵、真实探针、docs check、隐私门禁和暂存差异审阅；只暂存明确路径。

发布顺序：

1. `git commit`，提交信息写明用户可见结果和平台。
2. `git push origin <branch>`。
3. 创建与 `@version` 一致的 `vX.Y.Z` tag 并推送，不覆盖既有 tag。
4. 创建同 tag 的 GitHub Release，说明中区分三类证据和剩余限制。
5. 只读核对远端分支、tag、Release URL 和 raw master 版本/构建。
6. 在 `docs/maintenance/CURRENT.md` 追加发布回写；若需要提交回写，明确说明它不改变功能 tag。

关闭时报告：改动范围、文件、测试命令与结果、证据标签、限制、版本/提交/tag/Release、工作区状态和下一项最有价值的验证。
如果存在 `blocked`，报告阻断原因和恢复动作，不发送“全部完成”式模糊结论。

## 7. 交接模板

```text
### YYYY-MM-DD - 版本/工作区 - 范围
范围：<本轮要解决什么，不做什么>
改动：<文件与用户可见结果>
证据：<real-site verified / structure regression / blocked，附脱敏 URL 与状态>
检查：<命令与结果>
限制：<精确的剩余风险>
发布：<未提交 | 提交 | 已推送分支 | tag/Release>
下一步验证：<一项最有价值且可执行的动作>
文档更新：<更新了哪些入口/条目，是否触发拆分>
```
