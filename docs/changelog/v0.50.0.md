# OmniBlock v0.50.0

候选日期：2026-09-07
候选构建：`0.50.0-bili-lazy-uid-body-cleanup`
发布状态：本地候选，未 push、未创建 tag 或 GitHub Release；当前公开版本仍为
[`v0.46.2`](https://github.com/a2787/ub-utils/releases/tag/v0.46.2)。

## 用户可见变化

- B站「内容屏蔽（评论/弹幕）」入口固定到右下角，与设置齿轮同侧并位于其上方。统一入口创建、评论/弹幕模式切换和页面状态刷新都会重新应用这组位置约束。
- B站评论管理器和 AI 候选优先读取真实评论正文节点 `bili-rich-text`；同级的点赞、回复、举报操作组件以及 `bili-comment-menu` 不再被拼入正文或屏蔽依据。正文自身出现“点赞”“举报”等普通文字时不会被关键词清掉。
- B站原生弹幕列表只显示弹幕正文，不把行内的本地操作、平台操作或菜单文字混入显示内容。
- 单条、批量、播放器悬浮、原生弹幕列表执行屏蔽时，才会对本次目标的 `bili:dmhash:<hash>` 按需进行 CRC32 候选反查和匿名用户卡片校验；页面初始加载不会逐一反查全部弹幕 hash。
- AI 识别出的弹幕候选在用户点击「确认屏蔽所选」时复用同一条按需关联路径。唯一且完整校验的候选会同时保存 `bili:dmhash:<hash>` 与 `bili:uid:<uid>`；碰撞、多候选、请求失败或校验不完整时只保留 hash。
- AI 的人工审核、候选勾选和「确认屏蔽所选」门槛保持不变。“自动识别 UID”只免去逐个手动点击 UID 查询，不会让 AI 结果静默写入本地名单。

## 实现与安全边界

- B站评论适配器使用真站捕获的 `bili-rich-text`、`bili-comment-action-buttons-renderer` 和 `bili-comment-menu` 层级；没有正文节点的旧结构才使用排除操作组件的 Shadow DOM 深度文本兜底。
- 目标屏蔽动作通过同一个异步准备函数执行 UID 关联，并按 hash 缓存本次动作中的查询结果；查询期间只禁用当前按钮，不重建当前管理器或替换正在显示的内容。
- 只有 `status=ready`、非 partial、候选数恰好为 1 且用户卡片返回相同数字 UID 时才补入 UID。不可逆的 `mid_hash` 不会被伪装成已知 UID；CRC32 碰撞和任何不完整校验都保留 hash-only 边界。
- 没有改变 B站官方举报、拉黑、关注、发帖等平台写入行为；UID 卡片请求仍是匿名只读请求，不读取或导出 Cookie。
