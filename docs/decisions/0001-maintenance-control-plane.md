# ADR-0001：采用单一活动计划与可执行维护门禁

- Status: Accepted
- Date: 2026-08-30
- Scope: OmniBlock 的 AI 维护、验证、文档和发布流程

## 背景

OmniBlock 经过多轮快速迭代后已经拥有较完整的功能测试和若干维护文档，但计划主要散落在对话、
发布说明和事后交接中。当前状态、源码快照、真实站点证据和发布授权因此可能互相漂移。userscript
本身也已达到大型单文件规模，直接拆分会同时影响 document-start 顺序、Tampermonkey 元数据、
MV3 桥接和测试夹具。

## 决定

1. 使用 `docs/maintenance/PLAN.md` 作为唯一活动计划；用稳定 ID、状态、依赖、验收、证据和下一步动作连接需求、实现和交接。
2. 使用 `docs/architecture/ARCHITECTURE.md` 保存运行时边界，用短 ADR 保存不可频繁变化的架构选择；旧 ADR 不改写，以后用新 ADR supersede。
3. 扩展现有文档门禁，使计划字段、当前源码快照、版本/构建、链接、大小和隐私约束可被机器验证。
4. 当前任务中的明确授权才允许 push、tag、Release 或其他公开发布；历史授权不自动继承。
5. 在建立生成产物比对、会话 teardown 和回归覆盖之前，不进行一次性 userscript 全量模块化；先用受控的小范围清理降低风险。

## 后果

### 正面

- AI 接手时可以从活动节点恢复工作，不依赖完整对话历史。
- 计划冲突、过期快照和缺失证据能够在提交前被发现。
- 用户行为、当前事实、架构决策和历史记录职责分离，活动文档可以保持在预算内。
- 运行时重构会先经过行为等价和生命周期证据，不会因为追求形式上的模块化破坏注入链路。

### 代价

- 每个改动都需要维护计划状态和证据，短期文档工作量增加。
- 自动门禁无法替代真实站点观察和人工发布授权；不可验证条件仍会导致 `blocked`。
- 源码模块化会延后到有足够构建与回归基础之后。

## 被否决的替代方案

- 只增加一份不断追加的 AI 总说明：会复制规则并重新形成过大文档。
- 只依赖对话记忆：重启、分支或模型切换后无法保证状态连续。
- 立即把所有代码拆成多个文件：在没有产物比对和执行顺序契约时风险过高。
- 让自动探针把无法访问的网站当作通过：会混淆 `structure regression`、`real-site verified` 和 `blocked`。
