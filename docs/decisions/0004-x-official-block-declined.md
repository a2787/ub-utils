# ADR-0004：放弃接入 X 官方屏蔽功能

- Status: Accepted
- Date: 2026-11-19
- Scope: OmniBlock 对 X 平台屏蔽能力的边界与平台写入红线

## 背景

用户提出新需求：X 自带屏蔽黑名单没有实际上限，希望 OmniBlock 不再本地维护名单，而是直接触发 X
官方屏蔽，核心诉求是“识别 + 操作”一步完成。本轮只做桌面调研。

## 决定

1. 放弃：不接入 X 官方屏蔽，不新增针对 X 的平台写入或“识别即屏蔽”入口。这不是“技术上做不到”
   ——纯 UI 模拟点击有长期存活工具佐证——而是“风险收益比不成立”：省下的是点击次数，押上的是账号
   可用性。
2. `AGENTS.md`「AI 屏蔽安全闭环」中“绝不调用平台官方拉黑、举报、关注或发帖”的红线保持不变：
   未修订、未为 X 开例外。AI 仍只提候选，用户确认后才写入本地名单。
3. 本次评估没有产生任何代码改动，也没有触碰任何平台写入：不改 `omniblock.user.js`，不新增计划项，
   不运行登录态探针。
4. 工作重点回到已有平台的屏蔽能力完善。

## 四条技术路径评估

1. **纯 UI 模拟点击**：点击页面 Block 按钮，走已登录浏览器界面，与人工点击同构，不自造鉴权头；
   Red Block、x-bulk-blocker 等长期存活工具走这条。可靠性中等（依赖选择器），维护成本低到中，
   风控概率最低，收益仅是点击自动化。
2. **复用页面内 GraphQL/fetch 上下文（MAIN world hook）**：请求指纹与真实客户端一致，但仍需跟随
   queryId 与 `x-client-transaction-id` 算法变化，维护成本高，且属非公开接口。
3. **直接构造 GraphQL 请求**：queryId 随发版变化；`x-client-transaction-id` 需用页面 SVG 数据与 JS
   密钥实时计算，缺失该头是 X 判定自动化的关键特征（错误码 226）；ToS 禁止以非公开接口自动访问。
   维护成本很高，风控概率高。
4. **官方 API**：`POST /2/users/{id}/blocking` 文档逐字标注 “Enterprise plan only”，普通开发者拿不到；
   userscript 无后端，无法安全保管 OAuth 密钥。工程上不成立。

## 风险与依据

- **官方立场否定“识别即屏蔽”**：X block 端点文档要求只屏蔽用户点名或批准的账号，因为
  “finding or reviewing accounts is not approval to block them”，与识别即屏蔽直接冲突。
- **误伤是常态**：第三方抽样：13 条热门帖共 1,015 个回复作者中 59.7% 无任何垃圾特征，仅 7.6%
  具备两项以上特征。“一键拉黑所有回复者”大部分命中普通账号。
- **频控无官方阈值**：社区经验上限约 500 次/天（Red Block 作者据此自设，并注明“未见于任何官方
  文档”）；X 从未公布 block 数字阈值。
- **条款与封禁后果**：X ToS Misuse 条款含 facilitate：分发促成他人违规的产品本身亦违规；
  Developer Guidelines 写明 “Use only the official X API — No scraping, browser automation, or
  unofficial methods. Violations result in permanent suspension.”
- **官方通道已关闭**：X 已取消 CSV 批量导入/导出，“不维护本地名单、直接对齐平台”无官方通道。
- **用户决策**：用户表示放弃——“有道理，容易黑号，那算了，当我没说。不考虑 X 功能，我们对已有
  平台的功能进行完善就行了。”

## 后果

- 正面：避免为单一平台承担封号不可逆风险，维持“AI 出候选、用户确认、本地名单落地”的闭环；不为依赖
  非公开接口与选择器、需跟进 queryId/transaction-id 的路径增负担；投入收回到已有平台。
- 代价：“平台自带黑名单无上限、免维护”的收益无法实现，X 仍沿用需自行维护的本地名单；判断依赖上述
  调研与抽样，事实变化时重评。

## 重新考虑的前提

若重新考虑，须至少满足其一，且必须先修订 `AGENTS.md` 红线条款（不得绕过规则直接实现）：X 开放非
Enterprise 的 block API 且有明确配额；或用户接受在专用账号上做灰度实验并把频控压到极低。

## 验证边界与信息缺口

- 事实来自桌面调研；本轮无站点写入实验。
- 两处信息无可靠直接证据，不作结论依据，不得被后续乐观解读填补：批量 block 导致封号的公开案例
  （人数/速度/后果）缺少可靠统计；X 是否对 block 端点强制要求 transaction-id 未找到直接证据。
