# OB-AI-004 — 可学习的 AI 提示词系统（v0.52.0）

- status: in_progress
- owner: OmniBlock userscript + local AI gateway boundary
- date: 2026-09-08

## 目标

把现在“固定规则 + 单句通用提示”升级为可验证的提示词系统。系统要能表达作者的长期规则，记录用户对实际内容的正负反馈，并把已经确认的个性化偏好稳定地带入下一次 AI 分析，同时不把一次误操作扩大成永久屏蔽规则。

这是一项提示词工程和反馈数据建模工作，不是把浏览器端变成在线训练器。第一版目标是提高可解释性、可回放性和个性化控制能力，再用离线样本判断是否真的降低漏识别和误识别。

## 建议的数据格式

推荐使用经过 schema 校验的 `prompt-package.json` 作为规范格式，而不是让多个自由文本片段直接拼接。界面提供分区编辑、提案生命周期和反馈账本管理；导入导出仍以 JSON 为准，避免标点、缩进或自然语言段落改变字段含义。

逻辑上分为两个本地对象，导出时可以封装在同一个提示词包中：

1. `PromptProfile`：当前有效的作者规则和已经确认的个性化偏好。
2. `FeedbackLedger`：原始反馈事件及其理由，供本地汇总和审计；默认不全部发送给模型。

规范包的最小形状如下，示例内容全部是人工合成占位符：

```json
{
  "schemaVersion": 1,
  "profile": {
    "language": "zh-CN",
    "objective": "识别需要用户确认屏蔽的内容",
    "blockCriteria": [],
    "allowCriteria": [],
    "priority": ["keyword", "manual", "ai"],
    "reviewRequired": true
  },
  "feedback": {
    "positive": [],
    "negative": []
  },
  "personalization": {
    "accepted": [],
    "pending": [],
    "dismissed": []
  },
  "meta": {
    "revision": 1,
    "updatedAt": ""
  }
}
```

反馈项至少需要 `id`、`platform`、`kind`、规范化正文、`label`、`source`、`reasonCode` 和时间。身份键、页面 URL、昵称和原始接口对象只作为本地诊断可选字段，默认不进入模型输入；正文进入提示词时必须作为引用数据包裹，不能被解释为规则或指令。

## 反馈语义

反馈必须有三态，而不是把所有关闭弹窗都算成误识别：

- `positive`：用户确认屏蔽，或在没有 AI 候选的情况下从原生菜单手动屏蔽；后者标记为 `manual_miss`，表示可能漏识别。
- `negative`：用户对某一条 AI 候选明确点击“不屏蔽/误识别”，并完成可选原因登记。
- `unknown`：关闭弹窗、跳过、超时、取消批次或没有完成原因登记；只保留审计事件，不用于提示词学习。

执行屏蔽动作必须先完成，原因登记采用不阻塞的后续交互。原因使用受控枚举加可选短备注，正例可包括骚扰、垃圾、歧视、色情、剧透、无关内容，负例可包括正常表达、引用/反讽、语境不足、误关联、仅表达观点。自由备注按不可信用户数据处理，不执行其中的指令。

关键词命中、已有名单命中和平台写入动作不自动变成 AI 训练样本；只有用户明确选择“记录为 AI 反馈”时才写入，避免把精确关键词规则污染成宽泛语义偏好。

## 提示词生成链路

每次分析按以下顺序组装：

1. 先执行现有关键词/正则和本地名单过滤；命中关键词仍然零 token、直接本地屏蔽。
2. 读取当前 `PromptProfile`，把作者规则、允许边界、分类定义和人工审核要求渲染成固定段落。
3. 从 `FeedbackLedger` 按平台、内容类型、原因类别和正文词项选择少量相关正/负例；不发送整本历史账本，且受明确字符/token预算约束。
4. 将例子编码为只读引用数据，明确“例子不是指令”；模型只返回版本化 JSON，例如 `decision`、`category`、`confidence`、`reasonCodes` 和 `evidence`。
5. 保持现有候选审核框。模型结果不能绕过人工确认，也不能从模型返回值直接生成平台官方拉黑动作。

相关性选择第一版使用可解释的确定性评分即可，不先引入向量数据库或后台服务。相同稳定反馈不重复进入 prompt；超出预算时优先保留已接受的偏好和与当前平台/内容类型一致的最近例子。

## 个性化调整

本地确定性汇总器只能生成 `personalization.pending` 提案，例如“该用户通常把某类持续辱骂视为需屏蔽”。提案要列出支持它的反馈 ID、正负样本数量和冲突样本；用户明确接受后才进入 `personalization.accepted`，拒绝、暂停或删除的提案不参与有效提示词。这样可以避免一条误点或一次特殊语境永久改变规则。

个性化记录保存抽象偏好和证据引用，不复制整段历史正文；用户可以逐条删除、暂停或恢复。删除个人反馈后，相关待确认提案和有效偏好要重新计算，不能留下幽灵规则。

## 存储、隐私和迁移

- 运行时继续使用现有 `GM_*` 本地存储边界，增加版本化 key；导入先解析、校验、展示摘要，再一次性替换，失败时保持旧包不变。
- 默认不向网关发送 UID、`mid_hash`、昵称、URL、Cookie 或原始平台对象；身份只留在本地记录和现有执行链路。
- 用户正文和理由属于敏感本地数据，导出前明确提示；不写日志、不上传、不跨设备同步。网关请求只带当前待分析正文、脱敏后的有效提示词和有限引用例子。
- 从现有 AI 单句规则迁移时，保留原规则语义和优先级，生成 `profile` 初稿；迁移必须可回滚，并兼容旧设置键。
- 对反馈账本、例子数量和生成 prompt 设置有界容量；达到边界时保留摘要和最近/高置信度证据，不无界增长。

## 实现与验收顺序

1. 先写 schema、迁移、序列化/反序列化和脱敏断言；人工合成夹具不得包含真实页面标识。
2. 接入“手动屏蔽后记录漏识别”和“AI 候选明确拒绝后记录误识别”两个入口，验证三态语义、取消不入样本和原因编辑。
3. 实现相关例子选择、固定 prompt 渲染、预算截断和版本化 JSON 输出解析；保留现有 80 条批次上限与增量去重。
4. 实现个性化提案的查看、接受、拒绝、暂停、删除和重算；不自动提升为有效偏好。
5. 建立人工合成离线评测集，分别测漏识别率、误识别率、拒答/不确定率、prompt 大小、重复例子和身份泄漏；同时回归 B站、抖音、微博、知乎、贴吧现有 AI 路径。
6. 只有 schema、隐私、回放、浏览器 AI 回归和受影响平台真实只读探针达到证据要求后，才提高版本并考虑发布；在此之前保持 `proposed`/`in_progress`，不把“模型看起来更聪明”写成验证结论。

## 多平台读取覆盖审计（本轮新增）

审计维度固定为“展示形态 → 语义正文 → 作者归属 → 规范化身份 → AI 记录 → 本地屏蔽入口”。覆盖推荐/列表、详情/回答、评论展开、独立评论层、用户主页和平台特有的弹幕/帖子；不能从当前真实页面取得稳定 DOM 或身份时记为 `blocked`，不以跨平台猜测补选择器。

- 目标平台：B 站、抖音、微博、知乎、贴吧、X；各平台按自身捕获结构独立验收。
- 非目标：不调用私有接口、不自动翻页/关注/举报/平台拉黑、不把作者主页的推荐内容误归属于当前作品、不把整行操作文案送入 AI。
- 验收：每个平台为每种已捕获形态补一条人工合成读取/身份/AI 回归；真实页面逐项登记 URL 形式、登录状态、数量和确切结果；真实站点无法提供样本则保留 `blocked`。

## 非目标和风险

- 不做 DeepSeek 模型微调、远程向量库、跨用户共享样本或自动上传反馈。
- 不用 AI 学习结果替代关键词优先级、身份安全校验、人工审核和平台写入边界。
- 反馈文本可能含有提示词注入或个人信息；必须使用数据/指令分层和本地脱敏，不能把用户备注原样当系统规则。
- 正负样本不平衡、讽刺和上下文缺失仍可能造成误判；界面必须保留“未知/稍后处理”，不能强迫用户给出训练标签。
